# Оптимизация квалификаций GOVFOR

База изменений: `7a04d2acfd` (master после хотфикса #485). Ветка: `codex/govfor-performance`.
Проверки выполнены локально 5–6 октября 2026 года. На работающий сервер изменения не устанавливались.

## Исправленные источники нагрузки

- `SynchronizeRolePolicy()` больше не сортирует список профессий при каждом запросе допуска.
  Общая политика пересобирается после изменения версии хранилища, режима, исходного override
  или перезагрузки прототипов.
- `SendPolicy()` проверяет версию, доступность хранилища, режим, fail-open, полномочия текущей
  сессии и исходные требования до создания сетевого сообщения. Неизменившиеся политики
  не создают словари допуска, копии требований и строковую подпись. Принудительный запрос
  клиента всегда обслуживается; новая сессия с тем же UUID получает свою политику.
- `IsJobAllowed()` возвращает только результат проверки допуска. Список объяснений по-прежнему
  доступен через `CanTakeJob()`, но не создаётся при массовом опросе.
- `RecordSnapshot()` фильтрует историю до глубокого копирования: только выбранный игрок,
  разрешённые заметки/приостановки и последние 100 подходящих записей аудита для управления.
  Независимость изменяемых коллекций сохранена; чужая история не передаётся.
- Получение одной записи игрока, названия квалификации, аккредитации или инициатора
  приостановки больше не копирует всю базу.
- Статистика вычисляется один раз для опубликованной версии хранилища и выдаётся отдельным
  словарём каждому получателю. Слабая ссылка не удерживает старую базу в памяти после замены.
- Выдача квалификаций, запись участия и Execute миграции начинают копирование в фоновой задаче.
  Порядок игрового запроса сохраняется существующей очередью; блокировка изменений, CAS,
  атомарная запись и публикация только после успешного сохранения сохранены.
- Черновик изменения копирует индекс игроков, но глубоко копирует только изменяемую историю.
  Неизменённые истории используются совместно как неизменяемые данные. Определения,
  аккредитации, приостановки и прочие изменяемые метаданные по-прежнему копируются.
  ResetRecruit также получает собственную копию истории; неудачная запись не меняет
  уже опубликованные данные. Формат состояния и SQL-сохранение не изменены.
- PostgreSQL/SQLite при обычном обновлении читают JSON только при новой ревизии. Проверка
  ревизии и выбор тела выполняются одним SQL-запросом; отсутствие строки считается ошибкой,
  а восстановление связи на той же ревизии восстанавливает доступность.
  Инициализация схемы выполняется один раз на экземпляр репозитория. SQLite больше не
  захватывает write-транзакцию для обычного чтения.
- Обновление списка игроков открытых досье сравнивает повторно используемые записи без
  сортировки UUID и больших строк. Буфер завершённых запросов имён также используется повторно.
  Закрытые/удалённые bound-окна удаляются из списка получателей обновлений.

500 вызовов одной тестовой сессии не моделируют 500 действующих игроков с реальными
телами, сетевыми каналами, PVS и игровой нагрузкой. Время зависит от компьютера и прогрева.
Черновик по-прежнему копирует индекс игроков и метаданные, а сохранение сериализует полное
состояние. Общие паузы GC не исключены переносом операций в фон.

## Следующее крупное узкое место: сохранение

Текущий `Save()` всё ещё сериализует полное состояние и повторно записывает проекции
всех игроков, чек-листов и старого аудита при каждом изменении. В PostgreSQL отдельный
SQL-запрос выполняется на каждую такую запись. В SQLite текущие проекции прогресса
полностью пересоздаются. Перенос начала операции в фон уменьшает работу игрового
потока, но не исправляет стоимость этой записи.

Предложенный следующий этап:

1. Оставить полное каноническое состояние и CAS в одной транзакции.
2. Обновлять проекции только затронутых игроков; добавлять только новые заметки и аудит.
3. Ограничить очистку проекций прогресса UUID затронутых игроков.
4. Группировать запросы PostgreSQL вместо сетевого обмена на каждую запись.
5. Проверить перезапуск, сбой проекции/rollback, одновременные записи, исправление прогресса,
   миграцию, отзыв аккредитации и неизменность записей посторонних игроков на обоих движках.

**Этот этап не применён.** Автоматическая проверка отклонила выборочное сохранение
PostgreSQL/SQLite из-за риска необратимой потери квалификаций или аудита при ошибке
в проекциях. Запрошено отдельное разрешение пользователя.
